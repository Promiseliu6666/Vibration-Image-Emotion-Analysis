# Algorithm Decoupling and Versioned Weight Management Design

**Goal:** Decouple algorithm management from camera/runtime code so the frontend can manage algorithms, upload weights, and bind cameras to specific algorithm versions.

**Approved decisions:**
- Algorithms are maintained by the database, not generated by scanning folders.
- Algorithms do not need an applicable-scene field.
- One algorithm can have multiple weight versions.
- Weight files are stored on disk under `algorithm/weights/`; the database stores the path.
- Uploading a new weight creates a new algorithm version record instead of overwriting the old version.

## Backend Data Model

Keep the existing `xuzhou_alg` table as the algorithm-version catalog. One row represents one concrete runnable algorithm version.

Existing fields remain:
- `alg_id`: primary key for this algorithm version record.
- `alg_name`: display name shown in the frontend.
- `alg_serial`: stable algorithm code used by runtime and external devices.
- `alg_version`: version label for this weight/runtime variant.
- `alg_default_conf`: JSON default runtime parameters.
- `alg_common`: reserved metadata string.
- `alg_update_time`: update timestamp.

Add fields:
- `alg_weight_path`: server-side path to the uploaded weight file, for example `algorithm/weights/fire_detection/v1/fire.onnx`.
- `alg_enabled`: whether this algorithm version can be selected or started.

A unique constraint should prevent duplicate active version keys for the same algorithm code/version pair: `(alg_serial, alg_version)`.

## Backend File Layout

Use the root-level `algorithm/` package as the single home for algorithm runtime code and model resources:

```text
ruoyi-fastapi-backend/algorithm/
  __init__.py
  runtime_service.py
  registry.py
  weights/
    {alg_serial}/
      {alg_version}/
        uploaded_weight_file.onnx
```

`algorithm/runtime_service.py` remains responsible for resolving camera bindings into runtime bindings. Add a small registry/helper module only if needed for loading local algorithm implementations and validating weight paths.

Weight upload rules:
- Accept only known model extensions needed by the project, initially `.onnx`, `.pt`, `.pth`, `.bin`, `.engine`.
- Store the file under `algorithm/weights/{safe_alg_serial}/{safe_alg_version}/`.
- Sanitize filenames and never trust client-provided paths.
- Store only the server-side path in `xuzhou_alg.alg_weight_path`.
- Reject new records when `(alg_serial, alg_version)` already exists.

## Backend APIs

Extend the existing `/xuzhou/algorithm` controller instead of creating a second algorithm API family.

Required capabilities:
- `GET /xuzhou/algorithm/list`: return algorithm-version rows, including weight path and enabled status.
- `POST /xuzhou/algorithm/`: create algorithm metadata without weight if needed.
- `PUT /xuzhou/algorithm/`: edit algorithm metadata, default config, enabled status.
- `DELETE /xuzhou/algorithm/{alg_id}`: delete only when no camera is bound to that version.
- `POST /xuzhou/algorithm/upload-weight`: multipart upload that saves the file and creates a new version row.

Upload request fields:
- `algName`
- `algSerial`
- `algVersion`
- `algDefaultConf`
- `file`

Upload response includes:
- `algId`
- `algName`
- `algSerial`
- `algVersion`
- `algWeightPath`
- `algEnabled`

## Camera Binding Model

Continue using the existing video fields for binding storage to avoid introducing a new binding table in this step:
- `vidAlgorithm`: JSON list of selected algorithm-version objects.
- `vidAlgorithmName`: JSON list of display names.

Each bound item should contain enough information to run the exact selected version:

```json
{
  "algId": 12,
  "algName": "烟火检测",
  "algSerial": "fire_detection",
  "algVersion": "v1",
  "algWeightPath": "algorithm/weights/fire_detection/v1/fire.onnx",
  "algDefaultConf": { "threshold": 0.6 }
}
```

Runtime resolution should prefer `algSerial` as `algorithm_code`. `algId` remains the database reference. `algWeightPath` and `algDefaultConf` are passed through to runtime params.

When a camera starts:
- Parse `vidAlgorithm`.
- Verify each selected algorithm version still exists and is enabled.
- Verify the configured weight path exists when the algorithm requires a local weight.
- Return a clear error if a selected algorithm is disabled, deleted, or missing its weight.

## Runtime Behavior

Local algorithms and external-box algorithms stay unified under `CameraAlgorithmBinding`.

Extend runtime params so each binding can carry:
- `alg_id`
- `alg_version`
- `weight_path`
- `default_conf`

Local runtime uses the weight path to initialize the algorithm implementation. External-box runtime includes algorithm code/version/config in the command payload. Because no external box is currently connected, external runs can still enter `waiting_box` until a device callback arrives.

## Frontend Algorithm Management

Upgrade `src/views/algorithm/list/index.vue` into a full algorithm-version management page.

The page should support:
- List algorithm versions.
- Search by algorithm name and version.
- Show algorithm code, version, weight path, enabled status, and default config preview.
- Add/edit metadata.
- Upload a weight file to create a new version.
- Enable/disable a version.
- Delete only unbound versions.
- Bind selected algorithm versions to cameras.

For weight upload:
- Use Element Plus upload with manual submit.
- Show upload progress.
- Limit extension types to the backend-supported model formats.
- Do not read large files into memory as base64.
- Send multipart form data directly to the backend.

## Frontend Camera Binding

The existing camera binding dialog should bind cameras to specific algorithm versions, not just algorithm names.

Display labels should include version:
- `烟火检测 / fire_detection / v1`
- `安全帽检测 / helmet_detection / v2`

When saving bindings, write full version objects into `vidAlgorithm` and names like `烟火检测(v1)` into `vidAlgorithmName`.

## Error Handling

Backend should reject:
- Duplicate `(algSerial, algVersion)`.
- Unsupported weight file extension.
- Path traversal in uploaded filenames.
- Deleting an algorithm version that is still bound to a camera.
- Starting a camera with disabled or missing algorithm versions.

Frontend should show backend error messages directly when these cases occur.

## Testing

Backend tests:
- Uploading a weight creates a file under `algorithm/weights/{alg_serial}/{alg_version}/` and creates a database row.
- Duplicate version upload is rejected.
- Runtime resolution includes `algSerial`, `algVersion`, `algWeightPath`, and parsed default config.
- Disabled algorithm versions cannot be started.
- Deleting a bound version is rejected.

Frontend verification:
- Algorithm list loads version rows.
- Weight upload creates a visible new version row.
- Camera binding saves full algorithm-version objects.
- Binding dialog displays current camera bindings with version labels.

## Non-goals

This design does not add an applicable-scene field. It also does not introduce a separate camera-algorithm binding table; the existing `vidAlgorithm` JSON field remains the binding storage for this step.
