## 2. 启动时报错及修复

### 2.1 报错现象

在 `fatigue_model_bundle` 目录运行以下命令：

```powershell
python -m scripts.live_inference_local
```

出现：

```text
ModuleNotFoundError: No module named 'model_architecture.dataset'
```

### 2.2 原因

推理脚本曾从下面的训练模块导入窗口长度：

```python
from model_architecture.dataset.temporal_window_dataset import DEFAULT_WINDOW_STEPS
```

但 `fatigue_model_bundle` 是推理专用包，训练数据、数据切分和 Dataset 代码没有随包发布，因此该模块不存在。

### 2.3 修复方法

将窗口长度恢复为推理包内部常量：

```python
WINDOW_STEPS = 30
```

这个值表示 BiGRU 使用最近 **30 个一秒特征步**。它应与模型训练时的输入设置保持一致。

修复位置见 [live_inference_local.py](../fatigue_model_bundle/scripts/live_inference_local.py) 顶部的时间窗口配置。

### 2.4 验证结果

使用虚拟环境
`D:\Python\environments\fatigue-sense\python.exe` 进行了以下检查：

```powershell
python -m py_compile scripts/live_inference_local.py scripts/hud_text.py
python -c "import scripts.live_inference_local as m; print(m.WINDOW_STEPS)"
python verify_bundle.py
```

检查结果：

- Python 文件编译通过。
- 推理脚本可以正常导入。
- `WINDOW_STEPS = 30`。
- 眼睛、嘴部、姿态、BiGRU 和 MediaPipe 模型全部加载成功。
- 输出 `[OK] All bundle models loaded successfully.`。

完整的摄像头画面需要实际运行交互式推理程序验证，自动化检查只覆盖导入、模型和资源加载。

## 3. 右侧灰色底板

### 3.1 修改目的

左侧文字原本已有灰色底板，右侧专注度、分数、进度条和计数信息直接绘制在摄像头上。在浅色或复杂背景下文字不够清楚，因此为右侧增加相同类型的底板。

### 3.2 实现方式

在 [hud_text.py](../fatigue_model_bundle/scripts/hud_text.py) 中增加了通用函数 `draw_hud_panel()`：

- 对指定矩形区域进行半透明压暗。
- 默认透明度与左侧一致，均为 `0.45`。
- 自动将坐标限制在当前画面范围内。
- 左侧和右侧共用该函数，避免以后两侧底板样式不一致。

右侧主信息区在 [live_inference_local.py](../fatigue_model_bundle/scripts/live_inference_local.py) 的 `_draw_right_hud()` 中调用该函数。底板的位置会根据画面宽高计算，右侧保留边距。

可以把整个画面理解为：

- **左侧**：模型当前看到的数据、运行性能和最近一段时间的原始统计。
- **右侧**：根据左侧特征综合得到的专注度结果，以及累计行为次数。

单一指标偏高不等同于人员已经疲劳。左侧数据需要结合最近 60 秒的整体趋势一起看。

## 4. 左右面板指标说明

### 4.1 整体阅读顺序

<mark>建议按以下顺序阅读：</mark>

1. 先看右侧疲劳度和状态标签，了解当前综合结果。
2. 再看左侧的瞬时概率，确认眼睛和嘴巴是否被可靠检测。
3. 查看左侧 60 秒聚合特征，判断状态是短暂波动还是持续趋势。
4. 最后看姿态特征和关键点置信度，判断画面条件是否可靠。
5. 如果双手离开键盘或人员姿态变化较大，不应仅凭某个姿态数值下结论。

## 6. 左侧中间：单帧原始输出

| 显示字段   | 通俗含义                      | 判断方法                                   |
| ------ | ------------------------- | -------------------------------------- |
| 左眼闭合概率 | 模型认为当前左眼正在闭着的可能性，范围是 0～1。 | 越接近 1 越像闭眼。约大于 0.8 时可认为闭眼证据较强。         |
| 右眼闭合概率 | 模型认为当前右眼正在闭着的可能性。         | 含义与左眼相同。左右值短期差异较大可能来自侧脸、遮挡或检测误差。       |
| 张嘴概率   | 模型认为当前嘴巴正在张开的可能性。         | 越接近 1 越像张嘴。瞬间张嘴不一定是哈欠，需要持续时间和上下文。      |
| 姿态置信度  | 鼻子、两耳和两肩等关键点的平均检测置信度。     | 表示“人物关键点检测得是否可靠”，**不是**姿势标准程度，也不是疲劳程度。 |

这些数值只反映当前一帧，容易受眨眼瞬间、光线、摄像头角度和面部遮挡影响，不能单独作为疲劳判断。

画面中检测框上的 `L eye`、`R eye` 和 `mouth` 标签显示的是同一帧的概率；`BLINK` 或 `YAWN` 状态表示当前事件检测器正处于对应状态，并不代表右侧累计次数已经增加。

## 7. 左侧下半部分：每秒聚合特征

### 7.1 聚合方式

眼睛和嘴巴会保留最近约 **60 秒**的数据，并且每隔 **1 秒**生成一行聚合特征。

因此，显示名称虽然叫“每秒聚合特征”，实际上不是只统计当前这一秒，而是描述最近 60 秒的滚动状态。

### 7.2 字段说明

![](C:\Users\15826\AppData\Roaming\marktext\images\2026-11-03-12-02-28-image.png)

| 显示字段      | 通俗含义                                       | 阅读建议                                                    |
| --------- | ------------------------------------------ | ------------------------------------------------------- |
| 特征步 # 与时间 | 第几条聚合特征，以及程序运行到第几秒。                        | 第一条通常在预热约 60 秒后产生。                                      |
| 有效 / 无效   | 最近 60 秒中，眼睛和嘴巴是否有足够多的有效检测结果。               | 无效特征不会进入 BiGRU。有效标志目前主要检查眼睛和嘴巴，姿态数据会单独通过“关键点可见度”判断。     |
| 眼睛闭合占比    | 也就是 PERCLOS，最近 60 秒中眼睛闭合概率超过 `0.80` 的时间比例。 | 例如 `0.25` 表示约 25% 的时间疑似闭眼。它是疲劳判断中很重要的一项，但需要结合持续时间和其他指标。 |
| 眨眼频率      | 最近 60 秒内完成的眨眼次数，换算成“次/分钟”。                 | 在 60 秒窗口下，这个数值通常约等于窗口内完成的眨眼次数。                          |
| 平均眨眼时长    | 最近 60 秒内完成的眨眼平均持续多少秒。                      | 不完整或持续时间过短的瞬间不算完成事件。                                    |
| 眼闭合方差     | 最近 60 秒眼睛闭合概率的波动大小。                        | 数值越大表示眼睛状态变化越明显。它不是“越大越闭眼”的概率，也不能直接把方差当作疲劳等级。           |
| 哈欠频率      | 最近 60 秒内完成的哈欠次数，换算成“次/分钟”。                 | 哈欠需要满足持续时间和跨阈值条件，短时间张嘴通常不会计数。                           |
| 平均哈欠时长    | 最近 60 秒内完成的哈欠平均持续多少秒。                      | 只统计已经被判定为完成的事件。                                         |
| 张嘴比例      | 最近 60 秒中，张嘴概率超过 `0.70` 的时间比例。              | 数值高表示嘴巴经常张开，但可能来自说话、呼吸或打哈欠，需要结合哈欠事件判断。                  |
| 平均眼闭合     | 最近 60 秒内眼睛闭合概率的平均值。                        | 与 PERCLOS 不同：这里使用概率平均值，PERCLOS 使用超过阈值的帧数比例。             |
| 平均张嘴      | 最近 60 秒内嘴巴张开概率的平均值。                        | 这是连续概率的平均值，不是张嘴时间占比。                                    |

### 7.3 眨眼和哈欠检测阈值

为了避免概率在临界值附近来回跳动，代码使用两个阈值：

| 事件  | 开始条件              | 结束条件          | 最短持续时间   |
| --- | ----------------- | ------------- | -------- |
| 眨眼  | 双眼平均闭合概率大于 `0.85` | 低于 `0.70` 后结束 | `0.03` 秒 |
| 哈欠  | 张嘴概率大于 `0.80`     | 低于 `0.50` 后结束 | `1.50` 秒 |

这种方法可减少概率轻微波动造成的重复计数。

## 8. 左侧最下方：60 秒姿态特征

![](C:\Users\15826\AppData\Roaming\marktext\images\2026-11-03-12-02-46-image.png)

姿态特征来自最近 60 秒内的鼻子、两耳、两肩关键点。数值主要描述人物在画面中的相对位置和运动，不是医学角度测量。

| 显示字段   | 通俗含义                     | 阅读建议                                           |
| ------ | ------------------------ | ---------------------------------------------- |
| 头部俯仰   | 鼻子相对两肩中点的垂直位置，并用肩宽归一化。   | 显示的是归一化比例，不是度数。正负号表示鼻子相对肩膀偏下或偏上；持续低头或前倾时通常会变化。 |
| 头部侧倾   | 两耳连线的倾斜角，单位是弧度。          | 正负值表示头向左或向右歪。                                  |
| 肩部倾斜   | 两肩连线的倾斜角，单位是弧度。          | 数值接近 0 通常表示肩线较平；明显正负值表示身体或肩线倾斜。                |
| 头部尺寸比  | 两耳距离与肩宽的比例。              | 头部离摄像头更近、肩部检测异常或人物转身时都可能改变该值，不适合作绝对距离使用。       |
| 头部运动量  | 鼻子在相邻画面之间的平均移动量，并按肩宽归一化。 | 数值越大说明头部移动越多，可能来自正常动作、说话、晃动或姿态变化，不能单独说明疲劳。     |
| 头部垂直漂移 | 最近 60 秒鼻子垂直位置的标准差。       | 衡量头部上下波动程度，不是最终位移，也不是方向。                       |
| 姿态漂移   | 最近 60 秒两肩中点垂直位置的标准差。     | 衡量身体整体上下移动或下滑的程度。                              |
| 关键点可见度 | 当前姿态关键点检测的平均置信度。         | 越高表示关键点越可靠。如果平均可见度低于 `0.40`，姿态特征会被清零。          |

如果关键点可见度很低，而头部俯仰、侧倾、肩部倾斜、运动量和漂移等全部显示为 `0`，通常表示姿势检测不可靠，不代表人物姿势完美。

## 9. 右侧：综合结论

<img title="" src="file:///C:/Users/15826/AppData/Roaming/marktext/images/2026-11-03-12-03-21-image.png" alt="" width="165">

### 9.1 疲劳度分数

右侧大号数字是系统根据最近约 30 秒行为特征计算的疲劳度，范围为 0～1。

模型内部仍保留以清醒程度为方向的原始分数，页面显示时转换为：

```text
疲劳度 = 1 - 原专注度
```

**分数越高，表示疲劳倾向越明显；分数越低，表示当前越清醒。**

| 分数范围              | 状态文字 | 颜色  | 通俗解释            |
| ----------------- | ---- | --- | --------------- |
| `< 0.45`          | 清醒   | 绿色  | 模型认为当前疲劳倾向较低。   |
| `0.45` 到 `0.70`   | 困倦   | 橙色  | 模型认为已经出现困倦倾向。   |
| `> 0.70`          | 疲劳   | 红色  | 模型认为当前疲劳倾向明显。   |

分数条的长度直接对应大号疲劳度，条越长表示模型判断越疲劳。

### 9.2 原始值与平滑值

| 显示字段  | 通俗含义                                                                         |
| ----- | ---------------------------------------------------------------------------- |
| 原始值   | 当前一次模型输出的疲劳度，可能上下跳动。 |
| 大号疲劳度 | 经过指数滑动平均后的疲劳度，计算方式为 `40% × 当前原始值 + 60% × 上一次平滑值`。它<mark>更稳定，更适合作为画面主结果</mark>。 |

因此，大号数字和“原始值”不完全相同是正常现象。

### 9.3 预热状态

右侧尚未出现专注度时，会显示：

```text
预热 x/30
```

它表示正在为 BiGRU 收集 30 个有效的一秒特征：

- 前面的 60 秒用于填满眼睛、嘴巴和姿态的滚动窗口。
- 再收集 30 个有效特征步，通常约需 30 秒。
- 因此第一次出分通常约需 90 秒。
- 如果特征被判为无效，就不会加入时序窗口，预热时间会更长。

### 9.4 累计次数

| 显示字段 | 通俗含义                       |
| ---- | -------------------------- |
| 眨眼次数 | 从程序启动以来累计完成的眨眼总次数，不是每分钟次数。 |
| 哈欠次数 | 从程序启动以来累计完成的哈欠总次数，不是每分钟次数。 |

右侧累计次数和左侧聚合特征中的频率含义不同：

- 右侧是本次运行以来的累计总数。
- 左侧“眨眼频率”和“哈欠频率”是最近 60 秒内的滚动频率。

## 10. 指标的局限性

1. 疲劳度及模型内部的清醒分数来自规则生成的伪标签训练，主要参考 PERCLOS、眨眼、哈欠和姿态等行为特征，不是医学诊断。
2. 训练标签并不是经过医生或专业人员逐帧确认的疲劳等级，因此分数更适合表示行为趋势。
3. 单次闭眼、低头或张嘴不能直接说明人员疲劳。
4. 摄像头角度、光照、眼镜、口罩、人物距离和侧脸都会影响结果。
5. 如果眼睛、嘴巴或姿态关键点无效，应优先检查画面条件，再判断分数是否可信。
6. 系统更适合作为辅助提示，不应仅凭单次分数判断人员不能继续工作。

## 12. 平台集成问题追加记录

### 12.1 疲劳检测接口出现 503

曾出现页面返回 503，但排查后确认不是疲劳模型服务退出：

- 503 实际来自默认选中的小智摄像头没有新画面。
- `/video/shared/frame?source=xiaozhi` 持续返回 503。

处理结果：

- 疲劳检测页默认摄像头改为“本机摄像头”。
- 本地摄像头恢复正常。
- 切换摄像头来源时增加 Session 重置。

> 后续统一改造后，摄像头默认值改为沿用全局选择；切换时不再同步等待 Session 重置，旧分析会话在后台退出。详见第 13 节。

### 12.2 重置检测时报 `'Event' object is not callable`

原因：

- 疲劳服务线程的停止事件曾被命名为 `_stop`。
- `threading.Thread` 内部也存在 `_stop()` 方法。
- 自定义属性覆盖了线程内部方法，导致切换摄像头或重置时异常。

处理结果：

- 将停止事件重命名为 `_stop_event`。
- 验证“小智摄像头 → 本机摄像头”能够正常切换。



### 12.6 平台检测看起来不如原 OpenCV 窗口准确

主要差异不在模型权重，而在输入和显示链路：

1. 平台共享摄像头画面为 `640×480`。
2. 共享帧经过 JPEG 质量 80 压缩后再进入模型。
3. 疲劳服务默认目标帧率为 12 FPS。
4. 页面最初每 800 ms 查询一次检测 JSON。
5. 视频流和检测 JSON 来自两条不同链路，检测框可能滞后。

原 OpenCV 窗口直接处理摄像头帧，并在同一帧上立即绘制结果，因此视觉上更同步。

### 12.7 复用原 OpenCV 窗口的方案

`cv2.imshow()` 是本地桌面窗口，不能直接嵌入浏览器。

可复用的是窗口背后的：

- 模型加载
- 人脸关键点和眼部/嘴部裁剪
- CNN 分类
- 姿态检测
- HUD 绘制
- 特征聚合和 BiGRU 评分

最终采用“同帧服务端渲染”方案：

```text
摄像头帧
  -> 疲劳服务推理
  -> 在同一帧绘制关键点和可选检测框
  -> JPEG/MJPEG 输出
  -> 主后台流式代理
  -> 浏览器视频区域
```

这样检测框、关键点和视频画面来自同一帧，不再依赖异步 Canvas 对齐。

> 后续性能调整后，默认预览改为直接显示共享原始画面，分析结果独立更新；只有用户主动开启“显示检测框”时才切换到同帧分析画面。详见第 13.4 节。

### 12.12 问号图标尺寸异常

出现过两次尺寸问题：

1. 固定尺寸圆圈样式显得过大且不协调。
2. 四个数据窗口中由脚本动态生成的问号没有命中 Vue 作用域样式，实际被浏览器按默认 SVG 尺寸渲染为 `48～72px`。

最终修正：

### 13.2 小智摄像头与本地摄像头隔离

曾出现页面已经选择小智摄像头，但本机摄像头指示灯仍持续点亮。

原因是小智后台仍有一个共享摄像头桥接任务持续读取 `local`，并且本机 CameraHub 仍保持热连接。

处理结果：

- 选中小智实体设备时，自动停止残留的本机和 RTSP 共享摄像头桥接任务。
- 本机摄像头无请求后最长保留 10 秒，随后释放。
- 小智和 RTSP 摄像头保留 45 秒热连接，便于快速切回。
- 同一物理摄像头由 CameraHub 统一读取，分析服务只订阅共享帧。

### 13.3 摄像头切换性能优化

旧方案在切换时同步等待旧分析线程退出，最坏可能需要等待约 5 秒。

最终处理：

- 页面切换后立即订阅新摄像头，不再等待 reset 接口返回。
- 旧分析线程标记停止后在后台退出。
- 新会话启动时不阻塞页面首帧。
- 疲劳模型在服务启动阶段预加载，避免第一次切换时才加载模型。
- 旧会话最多保留 8 个引用供后台收尾，防止快速连续切换造成无限累积。

实测热启动后连续 reset 响应约为 `0.06～1.5 秒`，不再固定等待 5 秒以上。

### 13.4 原始画面和分析画面解耦

曾出现疲劳页响应头很快建立，但 6 秒内没有画面数据。原因是页面在等待疲劳模型完成第一帧处理。

最终显示策略：

```text
默认状态
  摄像头共享原始画面 -> 浏览器

开启“显示检测框”
  摄像头共享原始画面 -> 浏览器
  疲劳分析结果 JSON -> SVG 检测框叠加层
```

这样切换检测框时不会重新连接或重新编码视频流，只等待摄像头首帧，不等待 CNN、姿态和 BiGRU 完成；分析结果仍通过 JSON 在后台更新。

检测框坐标来自分析结果，刷新频率低于原始视频帧率，因此快速移动时检测框可能略有滞后，但视频本身保持原始预览的帧率和清晰度。`/fatigue/feed` 仍保留为服务端同帧渲染接口，供需要单帧一致性的客户端使用。

### 13.5 页面卡顿和后台资源释放

排查发现三个额外负载来源：

1. 本机原始视频流原为约 30 FPS，带宽约 `1.2 MB/s`。
2. 疲劳页面原每 800 ms 查询一次分析结果。
3. 部分路由被 `keep-alive` 缓存，离开页面后仍可能继续轮询和拉流。

最终处理：

- 原始预览流限制为 12 FPS。
- 本机流带宽实测从约 `1.2 MB/s` 降到约 `0.22 MB/s`。
- 疲劳结果轮询调整为 1200 ms。
- 疲劳路由设置为 `noCache`，离开时卸载页面并断开视频。
- 数据监控页失活时停止轮询、清空视频连接，重新激活时再恢复。
- 设备目录改为静默后台刷新，间隔 30 秒，失败不再弹出全局超时提示。

### 13.6 Vite 卡死和请求超时

- 视频加载后，从图像的 `naturalWidth`、`naturalHeight` 更新尺寸和画面宽高比。

### 14.3 小智摄像头连接不上：USB 采集进程未运行

**现象：** 小智摄像头显示离线，读取画面返回 503；主平台和疲劳服务仍可正常访问。

**排查结果：**

- 前端 `5173`、主后端 `9099`、小智后端 `8000` 和疲劳服务 `9101` 均正常响应。
- 主平台与小智服务使用的摄像头桥接密钥一致。
- USB 摄像头仍能被系统识别，当前物理设备对应 `COM9`。
- 已登记的采集进程 PID 已失效，系统中没有正在运行的 `watcher_usb.py` 采集进程。
- 设备目录能够正常读取，但由于没有新帧上传，设备状态为离线。

**根因：** `stop_local.py` 会停止 USB 采集进程，而 `start_local.py` 原来只启动小智后台服务，没有恢复 USB 采集。重新启动项目后，会出现“后台在线、摄像头不出图”的状态。

**现场恢复：** 使用现有采集控制逻辑，恢复已登记设备在 `COM9` 上的采集。恢复后，当前设备 `watcher-usb-sun` 显示在线；另一个历史设备记录当时仍为离线。

### 14.4 启动时恢复已登记的 USB 采集

为避免项目重启后再次遗漏采集，新增以下处理：

- `start_local.py` 在确认小智服务就绪后，调用 `resume_registered()`。
- `xiaozhi-study/app/device/capture_control.py` 新增 `resume_registered()`，按已登记的物理 USB 序列号查找当前端口，允许同一设备的 COM 编号发生变化。
- 仅恢复注册信息中仍有 PID、设备编号有效、未被删除且物理 USB 序列号匹配的采集任务。
- 用户主动停止采集时，注册信息中的 PID 会被清空，这类任务不会自动恢复。
- 未登记、已拔出或已删除的设备不自动恢复，也不会用其他物理设备替代。
- `set_running()` 新增 `restore` 参数；自动恢复使用 `restore=False`，不向采集进程传入 `--restore`，防止自动取消设备的删除状态。
- 已运行的采集任务复用原进程；单台设备恢复失败时记录错误，不阻断其他设备的恢复。

相关文件：
