## git提交

 以刚才这次合并为例，正确的提交流程是：

1. 确认当前目录和分支                                                                                              
   
   git status                                                                                                         
   git branch --show-current                                                                                          
   git remote -v                                                                                                      
   
   这一步确认了真正的仓库目录以及当前分支是 main。                                                                    

2. 检查本地是否有未提交内容                                                                                        
   
   git status                                                                                                         
   git diff                                                                                                           
   
   有未提交的重要修改时，应先提交，或临时保存：                                                                       
   
   git stash push -u -m "合并前暂存"                                                                                  
   git fetch origin                                                                                                   
   git merge origin/main                                                                                              
   git stash pop                                                                                                      
   
   不能在不了解本地修改的情况下直接强制覆盖。                                                                         

3. 先获取远程提交，再进行合并                                                                                      
   
   git fetch origin                                                                                                   
   git merge origin/main                                                                                              
   
   git pull 实际上通常等同于“获取远程提交 + 合并”。分开执行 fetch 和 merge 更容易判断每一步发生了什么。               

4. 查看冲突文件                                                                                                    
   
   git status                                                                                                         
   git diff --name-only --diff-filter=U                                                                               
   
   刚才的冲突文件是：                                                                                                 
   
   .gitignore                                                                                                         
   ruoyi-fastapi-backend/hik_vision/hik_vision.py                                                                     
   ruoyi-fastapi-backend/module_xuzhou/service/agent_service.py                                                       

5. 按“远程代码为准”解决冲突                                                                                        
   
   当前合并中，MERGE_HEAD 指向远程提交，因此可以这样处理：                                                            
   
   git restore --source=MERGE_HEAD --staged --worktree -- 冲突文件路径                                                
   
   这个命令会同时恢复文件内容并加入暂存区。刚才三个冲突文件都使用了远程版本。                                         
   
   如果只手动编辑了文件，则需要重新暂存：                                                                             
   
   git add 冲突文件路径                                                                                               

6. 验证冲突确实解决                                                                                                
   
   git diff --name-only --diff-filter=U                                                                               
   git diff --check                                                                                                   
   
   两条命令都没有输出，才表示没有未合并文件和冲突标记。随后最好运行项目测试或启动检查。                               

7. 提交合并                                                                                                        
   
   git commit --no-edit                                                                                               
   
   刚才生成的合并提交是：                                                                                             
   
   6a172a1 Merge branch 'main' of https://github.com/...                                                              
   
   它有两个父提交：                                                                                                   
- bada0ea：本地原有提交                                                                                            

- ee5ae45：最新远程提交                                                                                            
8. 再次确认结果                                                                                                    
   
   git status                                                                                                         
   git log -3 --oneline --graph --decorate                                                                            
   
   刚才完成后工作区干净，main 比 origin/main 领先 2 个提交。                                                          

9. 推送，等确认代码无误后执行                                                                                      
   
   git push origin main                                                                                               
   
   关键原则是：先检查状态，再获取远程；只覆盖明确允许覆盖的内容；解决冲突后验证、暂存、提交，最后再推送。不要一开始就 
   用 git reset --hard origin/main，因为那会连同未保留的本地提交和修改一起丢弃。

## 5. 启动 Redis 和 RabbitMQ

Redis 和 RabbitMQ 通过 Docker Desktop 运行。先启动 Docker Desktop，并等待 Docker 引擎进入运行状态。

### 5.1 先检查容器是否已经创建

```powershell
docker ps -a --filter "name=binhua-redis" --filter "name=binhua-rabbitmq" --format "table {{.Names}}`t{{.Status}}`t{{.Ports}}"
```

根据输出判断下一步：

- 状态为 `Up`：容器正在运行，不需要执行其他启动命令。
- 状态为 `Exited`：容器存在但已停止，使用 `docker start` 启动。
- 没有相关容器：这是首次运行，需要使用 `docker run` 创建。

当前机器已经创建过这两个容器，因此一般只需要启动已有容器，不要重复执行 `docker run`。

### 5.2 启动已经创建的容器

如果容器已经存在，执行：

```powershell
docker start binhua-redis binhua-rabbitmq
```

如果执行 `docker run` 时提示：

```text
Conflict. The container name "/binhua-redis" is already in use
```

说明容器已经存在，不是安装失败，直接改用 `docker start`。

### 5.3 首次创建容器

只有在 `docker ps -a` 中确认容器不存在时，才执行：

```powershell
docker run -d --name binhua-redis -p 6379:6379 redis:7-alpine

docker run -d --name binhua-rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:3-management
```

首次执行时 Docker 会自动下载 Redis 和 RabbitMQ 镜像。这一步只需执行一次。

### 5.4 检查运行状态

查看容器：

```powershell
docker ps --filter "name=binhua-redis" --filter "name=binhua-rabbitmq" --format "table {{.Names}}`t{{.Status}}`t{{.Ports}}"
```

正常情况下两个容器的状态都应为 `Up`：


检查 Redis：


## 13. 常见问题

### MySQL 提示 Access denied

```text

```

### RabbitMQ 连接失败

确认 Docker Desktop 已启动，并检查：

```powershell

```

本地 RabbitMQ 容器默认使用：

```text
用户名：guest
密码：guest
```

端口为 5672。

### 人脸信息上传失败

人员表 `xuzhou_people_face.group_id` 是指向 `xuzhou_people_group.id` 的外键。如果分组表没有对应记录，即使照片和模型都正常，最终保存人员时也会失败。

先检查分组：

```powershell
$mysql = "D:\AA_install\mysql-8.0.44-winx64\bin\mysql.exe"

& $mysql -h 127.0.0.1 -P 3306 -u root -p `
  --default-character-set=utf8mb4 `
  ruoyi_fastapi `
  -e "SELECT id, name, is_deleted FROM xuzhou_people_group ORDER BY id;"
```

系统的人脸识别默认使用第 1 组。如果分组为空，执行一次：

```powershell
& $mysql -h 127.0.0.1 -P 3306 -u root -p `
  --default-character-set=utf8mb4 `
  ruoyi_fastapi `
  -e "INSERT INTO xuzhou_people_group (id, name, created_time, updated_time, is_deleted) SELECT 1, '默认分组', NOW(), NOW(), 0 WHERE NOT EXISTS (SELECT 1 FROM xuzhou_people_group WHERE id = 1);"
```

创建后，在上传页面将分组 ID 填写为 `1`，然后重新上传正面清晰的 JPG 或 PNG 人脸照片。

如果仍然失败，检查后端 PowerShell 窗口中的 `添加失败: ...` 详细信息。常见原因还包括照片中没有可识别的人脸、图片内容不是有效的 JPG/PNG，以及 PaddleX 模型首次加载失败。

### Redis 连接失败

确认 `binhua-redis` 正在运行，并确认 `.env.dev` 中配置的是 `127.0.0.1:6379`。

- 人脸丢失 1.5 秒后重置。

## 人脸识别优先这样提升

  当前链路的计算量主要花在重复检测上：                                                                

  OpenCV SSD 检测一次                                                                                 
  → 裁剪人脸                                                                                          
  → PP-YOLOE_plus-S_face 又检测一次                                                                   
  → ResNet50_face 提取特征                                                                            
  → 余弦相似度                                                                                        

  建议按收益排序：                                                                                    

1. 先统一人脸检测器                                                                                 
   
   实时入口已经得到稳定人脸框，可以新增 extract_features_from_crop()，直接把裁剪并对齐的人脸送入    
   ResNet50_face，跳过第二次 PP-YOLOE_plus-S_face 检测。这样速度会更好，也避免两个检测器选中不同人  
   脸。                                                                                             

2. 增加人脸质量门控                                                                                 
   
   提取特征前检查：                                                                                 
   
   - 人脸尺寸是否足够                                                                              
   - 拉普拉斯方差是否低于模糊阈值                                                                  
   - 人脸是否接近画面边缘                                                                          
   - 曝光是否过亮或过暗                                                                            
   - 连续帧相似度是否稳定。                                                                        
   
   低质量图片不应进入特征库，也不应触发身份判定。                                                   

3. 每人登记多张模板                                                                                 
   
   当前数据库主要是一份 features 特征。建议每人登记 3-5 张：                                        
   
   - 正面                                                                                          
   - 轻微左右侧脸                                                                                  
   - 正常和较强光照                                                                                
   - 与实际摄像头距离接近的照片。                                                                  
   
   查询时保留多模板，或者用模板平均向量；这通常比直接换模型提升明显。                               

4. 增加 Top-2 Margin                                                                                
   
   现在只判断最高相似度是否超过阈值。建议同时要求：                                                 
   
   top1_similarity >= threshold                                                                     
   top1_similarity - top2_similarity >= margin                                                      
   
   例如初步使用 margin=0.05，再根据验证集校准。这样能明显减少“在相似人员中随机选中一个”的问题。     

5. 统一并校准阈值                                                                                   
   
   当前实时链路使用 0.4，外部接口默认 0.3，两者不一致。应按实际摄像头采集验证集分别计算：           
   
   - FAR：陌生人被误认率                                                                           
   - FRR：本人被拒绝率                                                                             
   - Top-1 准确率
   - 识别耗时。                                                                                    
   
   不建议凭感觉继续把阈值降到 0.25，否则误认会快速增加。                                            

6. 做人脸对齐                                                                                       
   
   使用 5 点关键点进行旋转和透视校正，再送入 ResNet50_face。侧脸、摄像头畸变和不同安装高度较多时，对
   齐的提升通常比简单换更大的网络更明显。                                                           

7. 最后才考虑微调识别模型                                                                           
   
   ResNet50_face 已经是不错的通用特征模型。如果完成上述步骤仍不足，再考虑：                         
   
   - 服务器：ArcFace 系列 ResNet50/ResNet100                                                       
   - 边缘设备：MobileFaceNet、轻量 ArcFace                                                         
   - 使用项目真实摄像头数据做度量学习                                                              
   - 使用 identities 和 impostor pairs，采用 ArcFace/CosFace 等 margin loss                        
   - 固定 backbone 微调，随后再解冻部分层。                                                        
   
   数据划分必须按“人员、日期、摄像头”分组，不能随机按帧划分，否则测试准确率会虚高。                 
   
   ## e1-e14 模型怎么建立
   
   当前公式存在两个需要先修正的问题：                                                                  
- 实时链路只累计 5 帧就开始计算全部指标。                                                           

- Welch 频谱要等至少 20 组能量，很多 e3、e7、e11、e12、e14 在预热阶段其实仍是默认值或零值。         
  
  因此应先增加：                                                                                      
  
  analysis_ready = false                                                                              
  warmup_frames = 100 左右                                                                            
  
  在收集足够数据前返回 null，不要返回看似有效的默认值。同时记录实际 FPS、丢失帧数和人脸质量分数。     
  
  真正训练情绪指标时，建议：                                                                          
1. 建立按 Session 标注的数据集，例如每段 10-30 秒。                                                 

2. 标签使用成对比较或经过验证的量表，例如压力、疲劳、愉悦程度；不要直接把现有 e1-e14 当作真实标签。 

3. 从原始振动数据中提取特征：                                                                       
   
   - 振幅均值、方差、分位数                                                                        
   - 左右脸振幅差                                                                                  
   - 频谱峰值、主频、频带能量                                                                      
   - 时间窗口统计量                                                                                
   - 人脸尺寸、运动速度和光照质量。                                                                

4. 第一阶段使用 LightGBM、XGBoost、随机森林或 Ridge Regression，建立可解释基线。                    

5. 按人员分组做交叉验证，避免同一人员的片段同时出现在训练集和测试集。                               

6. 基线稳定后，再考虑 1D-CNN、TCN 或视频时序 Transformer。                                          

7. 如果希望识别明显的表情，可以额外接入 Face Action Unit 模型；但面部表情不能直接等同于压力、疲劳或 
   健康状态。
